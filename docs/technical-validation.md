# LinkSpace 技术验证计划（第 1 周）

> 对应方案第十一章「第 1 周：技术尽调」与第十五章「建议立即执行的第一件事」。
> 本文件是**执行清单 + 记录模板**。验证结论直接决定后续排期，请如实记录失败项。

---

## 0. 为什么先做这两件事

方案第十五章点出两个最大未知项，它们分别卡住不同的东西：

| 验证项 | 卡住什么 | 失败后果 |
|---|---|---|
| scrcpy 投屏/控制/无线/多设备 | 第 2 周的桌面原型、P0 核心功能 | MVP 的核心价值受损，需自研替代，成本大幅上升 |
| Windows IddCx 虚拟显示器 | 第 2–4 个月的扩展屏幕、P2 差异化能力 | 扩展屏幕降级为普通投屏，产品差异化减弱但不致命 |

**两者互不阻塞，应并行推进。** scrcpy 由主产品路径执行，IddCx 在 `native/virtual-display` 独立进行。

## 3. Windows IddCx 虚拟显示器验证清单

**独立性要求**：在 `native/virtual-display` 下进行，不写入主产品代码。

### 3.1 起步

1. 安装 Visual Studio + Windows SDK + WDK。
2. 拉取微软官方 Indirect Display Driver 示例。
3. 按文档编译并在测试机安装（测试机建议为虚拟机，避免驱动问题影响主力机）。

### 3.2 验证项

对应方案 9.4 的五个前置问题：

| # | 问题 | 方法 | 结论 |
|---|---|---|---|
| 3.2.1 | 目标 Windows 版本能否稳定创建虚拟显示器 | 安装驱动后查看显示设置与设备管理器 | |
| 3.2.2 | 能否获取并处理显示帧 | 在示例的帧回调中输出统计/存图 | |
| 3.2.3 | Android 平板能否达到可接受延迟与画质 | 传输到平板实测 | |
| 3.2.4 | 断网/睡眠/重连能否恢复 | 人为制造异常 | |
| 3.2.5 | 驱动能否被普通用户安装/更新/卸载 | 走完整安装卸载流程 | |

### 3.3 补充风险项

| # | 项 | 结论 |
|---|---|---|
| 3.3.1 | 驱动签名要求（测试签名 vs 正式签名） | |
| 3.3.2 | 获取 EV 代码签名证书的成本与周期 | |
| 3.3.3 | 驱动崩溃是否导致系统不稳定 | |
| 3.3.4 | 与远程桌面/显卡驱动的兼容性 | |
| 3.3.5 | Windows 更新后驱动是否需要重新适配 | |

**停止判据**：若 3.2.1 或 3.2.2 无法在 2 周内通过，建议暂停扩展屏幕投入，转而先做「高质量投屏式第二屏」，把差异化放到体验层而非驱动层。
