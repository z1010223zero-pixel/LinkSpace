# LinkSpace 威胁模型

> 状态：随实现持续更新（2026-10-30 登记 2026-10-29/30 两轮审查修复对应的缓解）。
> 范围：局域网内的设备发现、配对、文件传输、投屏控制、键鼠共享。
> 不在范围：云端服务（第一版不存在）、物理设备被盗后的离线取证、Android 系统自身漏洞。

---

## 1. 资产

需要保护的资产，按价值排序：

| 资产 | 说明 | 泄露/破坏后果 |
|---|---|---|
| A1 远程控制权限 | 控制对方鼠标键盘的能力 | 高：等同于接管设备 |
| A2 文件系统访问 | 读写对方文件的传输能力 | 高：数据泄露或破坏 |
| A3 剪贴板内容 | 常含密码、密钥、隐私文本 | 高 |
| A4 设备身份密钥 | 长期身份凭据 | 中：可被冒充 |
| A5 屏幕内容 | 投屏与扩展屏画面 | 中 |
| A6 设备在线状态与拓扑 | 谁在家、有哪些设备 | 低但属隐私 |
| A7 应用可用性 | 不崩溃、可恢复 | 中：影响可用性 |

## 2. 信任边界

```
  互联网 / 其他网段
  ┌─────────────────────────────────────────┐
  │  局域网以外的任何主机                      │
  └───────────────┬─────────────────────────┘
                  │  ← 边界 0：网络范围边界（来源地址门禁）
  ┌───────────────┴─────────────────────────┐
  │  不可信网络（局域网）                      │
  │  未配对设备 / 同一网络下的其他主机           │
  └───────────────┬─────────────────────────┘
                  │  ← 边界 1：网络边界
  ┌───────────────┴─────────────────────────┐
  │  已配对但未授权控制的设备（只有 file 权限）   │
  └───────────────┬─────────────────────────┘
                  │  ← 边界 2：授权范围边界
  ┌───────────────┴─────────────────────────┐
  │  已授权控制的设备                          │
  └───────────────┬─────────────────────────┘
                  │  ← 边界 3：进程边界
  ┌───────────────┴─────────────────────────┐
  │  本机：主进程 / 子进程 / 本地存储 / 驱动     │
  └─────────────────────────────────────────┘
```

**局域网不等于可信。** 这是整个威胁模型的出发点：家庭网络可能有访客 WiFi、公司网络有未知设备、公共 WiFi 常有同网段扫描。因此方案 6.4 强调「发现不等于可信」。

**边界 0 与边界 1 互不替代。** 边界 1 及以内管的是「敲门的人是谁」——身份、授权范围、任务令牌；边界 0 管的是「谁有资格敲门」——来源地址必须落在 RFC1918 / 链路本地 / ULA 范围，否则在 TLS 握手阶段就断开。少了边界 0，一台装了 VPN 或虚拟网卡的机器会把端口一并开到可路由网段上，身份门禁再严也挡不住暴露面本身。

## 3. 威胁与缓解

### T0 端口暴露到局域网之外（Exposure）

**威胁**：机器装了 VPN、Hyper-V / VMware 虚拟网卡、ZeroTier 等，会多出拿到可路由地址的网卡。数据面若监听 `0.0.0.0`，端口会一并开到这些网卡上，任何能路由到本机的主机都能敲门——此时身份门禁（T1–T3）虽然还在，但攻击面已经扩大到整个可路由网络。

**缓解**：
- 监听地址自动选择：优先绑到唯一的局域网 IPv4；挑不出来才监听全部地址。
- 无论最终绑到哪个地址，入站一律过**来源地址门禁**：来源不属于 RFC1918 / 链路本地 / IPv6 ULA 范围时，在 TLS 握手阶段直接断开。
- 门禁同时挂在数据面的 `secureConnection` 与控制面的 `upgrade` 上。后者必须单独判一次——`upgrade` 不经过普通请求链，漏掉它等于门禁形同虚设。
- 逃生口 `LINKSPACE_ALLOW_WAN=1`，供跨网段调试使用，启用时日志留痕。

**残余风险**：IP 段判定拦不住「局域网内但不可信」的主机（那是边界 1 的职责）；也拦不住同源 IP 段内的跨网段路由。判定表本身有单元测试覆盖（`npm run verify:net`，含 172.16/12 边界与 IPv4 映射地址）。

**刻意取舍（审查 P3 登记）**：来源门禁对 CGNAT 段（100.64/10，Tailscale/ZeroTier 等 VPN overlay 常用）**放行**，与发现层 `pickLanInterface` 排除 CGNAT 的判据不同——发现层要跑 mDNS 组播（CGNAT 网卡跑不了），门禁层只看地址属性且不想误伤 VPN 场景。两处判据不同是有意的：VPN overlay 内的入站只剩 TLS 身份门禁（T1/T2）兜底，信任清单之外的连接拿不到任何授权。

### T1 冒充设备（Spoofing）

**威胁**：攻击者在局域网内广播同名/同类型 mDNS 服务，诱导用户配对，从而取得文件访问或控制权。

**缓解**：
- mDNS 广播不携带任何密钥材料。
- 配对必须经配对码或公钥指纹确认（TOFU），且需**双方**确认。
- 已配对设备再次连接时校验已持久化的指纹，指纹变化必须告警并暂停，不允许自动接受。
- **已信任设备必须出示 TLS 证书**：无证书或证书指纹与库存不符一律断开（2026-10-30 修复「自报指纹回退冒充」漏洞——此前无证书连接自报受害者指纹即可顶替身份）。
- `device.rename` 只接受信任清单内连接的改名请求，陌生连接的改名一律忽略并告警，不给未认证连接改写本机状态的通道。
- UI 上显示设备类型、首次配对时间，帮助用户识别异常。

**残余风险**：用户不核对配对码直接点确认。缓解方式是 UI 强制展示且不允许一键跳过。

### T2 未授权控制（Elevation of Privilege）

**威胁**：已配对用于传文件的设备，越权发起控制会话。

**缓解**：
- 配对时授权范围 `trustScope` 显式区分，控制能力默认**不在**基础范围内。
- 每次控制会话启动前被控端弹出可见确认（方案 14.1），会话结束即失效。
- 未授权请求返回 `SCOPE_DENIED`，不降级为「先允许再提示」。
- 输入事件注入前三重校验（连接身份 == 会话对端、sessionId 匹配、整批解码通过），坐标映射后钳进屏幕边界，非法事件整批丢弃。
- 受控期间强制退出本机输入采集（防本机沦为输入中继）；心跳超时立即终止会话并 releaseAll 恢复本机输入。

### T3 中间人攻击（Tampering / Info Disclosure）

**威胁**：局域网内 ARP 欺骗或 DNS 劫持，截获文件与剪贴板内容。

**缓解**：
- 控制与文件通道均强制 TLS，不接受明文降级。
- 自签证书 + 指纹绑定，连接时校验指纹与持久化值一致，不一致即断开。
- 不使用「首次连接自动信任一切」的宽松策略。
- `clipboard.share` 仅持有 clipboard 授权的对端可收发（配对默认只授 file + clipboard），文本上限 512 KiB，超出不发送。

**残余风险**：无 CA 环境下无法防御首次配对时的 MITM。这正是要求双方核对配对码的原因——配对码需经带外（人眼比对）确认。

### T4 拒绝服务（Denial of Service）

**威胁**：大量伪造的配对请求、超大文件、洪泛心跳导致应用不可用；或投屏子进程耗尽资源。

**缓解**：
- 配对请求限流（每设备每分钟 N 次），pending 状态超时清理。
- 传输前有大小确认，单文件与总大小上限可配置。
- 心跳与消息有频率上限，超限断开。
- 子进程数上限，会话退出超时强制 kill。
- **断网时的输入恢复**：键鼠共享断开必须立即恢复本机输入（方案 8.1），不能让用户「鼠标卡在别人屏幕上」。心跳超时路径已直连会话终止（不等 ws 关闭超时，2026-10-30 修复）。
- 控制通道单条消息上限 1 MiB；`input.event` / `clipboard.share` 超频断开（`verify:heartbeat` 洪泛用例钉死）。
- 对端离线的等待任务补发前复查信任与授权；撤销信任级联取消该设备全部未完成任务（2026-10-30 修复撤销后补发链开放）。

### T5 敏感信息泄露到日志（Info Disclosure）

**威胁**：日志与崩溃转储里出现剪贴板明文、文件绝对路径、密钥、配对码。

**缓解**：
- 日志只记录：设备 ID 前缀、消息类型、错误码、字节数。不记录内容。
- 剪贴板日志只记字节数与设备 ID 前缀，不记录内容，也不记录内容摘要（「摘要」是草案遗留措辞——内容派生值同样可能泄露信息）。
- 文件路径记录目录层级而非完整路径，或提供开关关闭。
- 崩溃上报（如有）前做同样脱敏。

### T6 本地存储被读取（Info Disclosure）

**威胁**：其他本地进程或恶意软件读取 `devices.json` 中的指纹与配置。

**缓解**：
- 密钥材料使用 Electron `safeStorage`（Windows 上依托 DPAPI，绑定用户账户）加密。
- 存储目录使用用户级权限，不写入 ProgramData 等全局可写位置。
- 不持久化传输历史。

**残余风险**：同用户权限下的恶意进程仍可读取。第一版接受此风险，不做进程隔离。

### T7 无线 ADB 暴露（Tampering / EoP）

**威胁**：为方便而常开 TCP 5555，导致同一网络任何人可调试手机（无需认证，旧版 ADB 尤其危险）。

**缓解**：
- **默认关闭**，开启需显式授权且明确提示风险（方案 7.3）。
- 提供一键关闭入口。
- 断开设备时清理 adb 连接状态。
- 优先使用 Android 11+ 的无线配对（需配对码）而非直接开放 5555。

### T8 驱动层风险（EoP）— 扩展屏幕

**威胁**：虚拟显示器驱动运行在内核态，缺陷可导致系统崩溃或被利用提权。

**缓解**：
- 独立仓库验证，不随 MVP 发布。
- 必须解决签名、安装、卸载、回滚与恢复方案后才可分发（方案 14.9）。
- 提供安全模式下的禁用方式。

### T9 供应链风险

**威胁**：集成的第三方组件（scrcpy 及其依赖、Electron 依赖树）引入漏洞或许可证问题。

**缓解**：
- 建立并维护 SBOM，见 `docs/license-inventory.md`。
- 固定依赖版本，启用 lock 文件，定期审查。
- 分发前核对二进制与其依赖的再分发条件。

## 4. 明确不做的事

写下这些是为了避免后期误以为"已覆盖"：

1. **不做跨公网直连。** 第一版全部能力限于局域网。跨网段需求留待云端方案评估。
2. **不做自动信任。** 任何"省事"的自动接受都会破坏 T1/T3 的缓解。
3. **不做隐蔽的后台控制。** 被控端必须有持续可见的"正在被控制"指示。
4. **不收集遥测。** 第一版无使用统计上报，避免引入额外隐私负担与合规义务。
5. **不保存剪贴板历史。** 只做转发，不做存储。
